# Web 后端

框架跑在 JVM 里，浏览器只做画布。这一页记的是设计思路与实测数据；用户怎么用写在核心库的
`docs/`（正式文档只放核心库），这里不重复。

## 形态

与其它后端一样是四件套（渲染器 / 元数据 / 工具 / 输入），多出来的一件是**帧可以被外部取走**：
浏览器按自己的节奏要一帧，后端把树走一遍、把绘制调用记下来，交给传输层。所以这里没有窗口、
没有渲染循环，也没有任何 Minecraft 类——它不依赖游戏，只依赖核心库。

进程里只发布一个渲染后端（`platformReady` 单次），所以这个后端要么取代游戏内渲染，要么由
宿主自己决定谁发布。宿主可以是独立 JVM，也可以是游戏内的模组；两种情况下这个后端看到的
世界是一样的。

## 记录器

渲染器实现是**记录**而不是绘制：每个绘制调用追加成一条定长/自描述记录。

- **不做批处理**，所以不需要在作用域切换时 `flush()`。框架自己调的 `flush()` 记为帧末。
- **不求交、不复合变换**：裁剪与变换各记一对 push/pop，客户端按顺序维护自己的栈。做第二遍
  只会多一个出错的地方。
- **资产表跨帧存活**：一个 id 只在首次出现时定义，之后按索引引用。稳态帧因此一条定义都没有，
  而第一帧（客户端起步的 keyframe）带全部定义。
- 未测量的矩形（`Measure` 为 NaN）按框架的约定当作"什么都不画"，与其它后端一致。

## 线上格式

一帧就是一维 32 位字数组，`[opcode, payload...]` 重复。浮点走 raw bits。两点是刻意的：

- 记录器写出来的 buffer **就是**载荷，没有第二次编码，也没有两套需要保持一致的结构；
- 帧间补丁退化成字的比较——相等、公共前缀、公共后缀都是 `Int` 比较，这才让"每帧做差分"变得便宜。

变长记录（带/不带纹理的 quad、三角形列表、资产定义）把形状写在载荷头几个字里，因此 stride 由
`Op.strideAt` 读出来而不是查表。记录器、报告、SVG 写出器、客户端都走同一个函数——这是格式唯一的
权威定义。

## 三种消息

| 消息 | 什么时候发 | 大小 |
|---|---|---|
| `NOCHANGE` | 与客户端持有的那一帧逐字节相同 | 1 字节 |
| `KEYFRAME` | 第一帧、重连、尺寸变化、客户端基帧不匹配 | 9 + 帧长 × 4 |
| `DELTA` | 其余情况 | 17 + 字面量 × 4 |

补丁**不带后缀**：字面量之后的尾部是客户端已经持有的，所以只传前缀长度和一段字面量。这也是补丁
与裁剪/变换栈相容的原因——那些记录和别的记录一样在流里，而客户端是**整份重放**的，一段从裁剪
作用域中间开始的字面量永远不会被单独解释。

补丁不划算时（字面量多到接近整帧）直接退回 keyframe：实测树结构变化的那一帧就是这样。

## 资产与字体

- **资产**：`ImageHolder` 只有 id 与声明尺寸，像素不在协议里。id 定义一次，之后每帧只传索引；
  像素将来走 HTTP（可缓存、可并行、不阻塞帧），永不进帧流。
- **字体**：布局在服务端（框架自己算），所以**量宽在服务端、客户端只按位置画**。这条决定了字体
  保真只有两条路：把同一个字体文件也给浏览器，或者把游戏字形栅格化成图集连 advance 一起发。
  现在是一张近似游戏字体的 advance 表，等客户端有真实字形时替换，格式不动。
- **本地图片**：只读尺寸（布局与 UV 需要），像素同样留给传输层。

## 输入

框架一半读事件、一半**轮询**（`isKeyDown`/`isMouseDown`/`mouse`），浏览器只给前者，所以轮询态由
事件流推导——按帧去问一次会往每帧前面塞一个往返。

丢焦或断线后再也收不到抬起事件，所以 `blur()` 清空所有按键与鼠标位置，否则那个键永远按着。

输入码点可能是增补平面（一个码点、两个 UTF-16 单元），要拆成代理对再喂给框架，否则会被截成
高代理。每个入口都包了 try/catch：组件的事件处理器是用户代码，异常不能把输入链路带走，返回
"未消费"就是框架本来会得到的结果。

## 缩放

沿用窗口后端的公式（`min(宽/320, 高/240)`，下限 1.0，刻意不取整）：没有游戏可问，而浏览器与
Java2D 都会抗锯齿，取整只会浪费分辨率。

## 传输层

`gradlew serve -Ppage=<页面> [-Pport=<n>]` 起一个 HTTP + WebSocket 服务；`/` 给页面，`/client.js`
给客户端脚本，`/ws` 是帧流与输入。

- **一次渲染、按连接编码**：框架一个进程只有一棵树，所以帧只取一次，然后对每条连接各自编码
  （每条连接持有的基帧不同）后广播。渲染进行中收到的 tick 直接丢弃，不排队——这正是差分设计
  假定的规则，也是慢客户端不能把服务端拖垮的原因。
- **视口是共享的**：根矩形是进程级的，任何一条连接 resize 都会改变所有人的布局，于是所有会话
  的基帧作废、下一帧全部发 keyframe。
- **线程**：所有碰到框架的事都在 `WebUtils.frameExecutor` 这一个线程上（框架的上下文绑定创建它的
  线程）；socket 读线程只解析命令然后交过去。帧因此只由帧线程写，而捕获请求可能来自别的线程，
  所以每个会话的写出都走一把锁——WebSocket 消息不能交错。
- **`capture` 是唯一的反向成员**：像素在浏览器里，服务端发一条 `capture` 文本命令，客户端
  `canvas.toBlob()` 后用**二进制**消息回传，服务端写盘并完成那次挂起的调用。`serve -Pcapture=<文件>`
  就是这套流程的验收：等服务端拿到图就退出。
- **输入由服务端翻译**：客户端只转发平台原样（DOM 的 `event.code`、按钮号、修饰键位），框架的
  按键常量在服务端，映射也就放在服务端；未知按键按 `Key.custom` 的扩展段哈希，保证同一个键每次
  都是同一个码。

## 实测

`gradlew measure -Ppage=<页面> -Pframes=<n> [-Psvg=<文件>]` 录真实演示页（1280×720）：

| 页面 | 整帧 | 稳定态上线 | 相同帧 | flush/帧 | 字数构成 |
|---|---|---|---|---|---|
| text | 14600 B | 1 B | 11/11 | 8 | text 98% |
| scroll | 13088 B | 1 B | 10/11 | 80 | text 88% |
| entry | 12356 B | 1 B | 14/15 | 20 | text 332 个 |
| color | 8124 B | 1 B | 11/11 | 32 | quad 49% / text 41% |
| layout | 8260 B | 1 B | 15/15 | 39 | text 205 个 |
| render | 20180 B | 1 B | 14/15 | 38 | text 385 个 |
| animation | 252 B | 41 B | 0/11 | 3 | 变化帧补丁 59 B |

四点结论：

1. **同帧短路是主要收益**：静态页面逐字节相同，一帧 1 字节。
2. **前后缀补丁对"变化帧"有效**（animation 59 B vs 252 B，且没有退化成 keyframe），但**树结构一变
   就退化**（scroll 那一帧 2708/3272 字都是字面量）——需要分块差分时才做。
3. **文字是最大开销**：text 页 98%、scroll 页 88% 的字数都是逐字符记录（9 字 = 36 B/字符）。合并成
   run 是下一个杠杆。
4. **每帧 3–80 次 `flush()`**（scroll 页 80 次）：批次被切得很碎。这条数据同时反馈给了核心库的
   `docs/dev/render.md`——"裁剪与变换随顶点携带"能同时去掉这些批次断点与那次 flush。

整帧记录耗时中位数 0.7–5.8 ms（含框架自身的构建与布局，与后端无关）。

## 未决

浏览器里的实测暴露了两处**看得见**的问题（都是已知近似的产物，不是传输问题）：

- **文字间距**：advance 是服务端的近似表，浏览器按自己的字体画，窄字符（`i`/`l`）会叠在一起。
  干净的解法是让**客户端把度量报上来**：连接后 `measureText` 一批字形发给服务端，服务端用真实
  advance 布局。这样既不用发字体文件，也不用赌字体一致——布局仍在服务端，只是度量来自真正要画
  的那一方。
- **三角形没有逐顶点插值**：canvas 2D 没有重心渐变，客户端现在按三角均值平铺，所以调色板的三角
  是平的（四边形没问题，轴对齐的两色渐变是精确的）。可选做法是细分三角形，或照窗口后端的做法用
  一张小纹理做仿射色场。

其余待办：

- **文字合并成 run**：格式加一条 run 记录（样式 + 逐字符 x），把 36 B/字符降到 8–12 B。
- **分块差分**：等有真实交互数据，看前后缀退化的频率再决定。
- **像素与翻译**：HTTP 端点 + 浏览器缓存（游戏 jar 与模组 jar 的贴图、字形图集、字体文件），
  以及把核心库的语言文件发给客户端（现在 tooltip 显示的是翻译键）。
- **反向成员**：`clipboard`/`openUri`/`narrate`/`playButtonSound` 也要反向消息；`capture` 已完成。
- **多客户端**：帧流可以广播（编码一次），但布局依赖视口尺寸，所以按尺寸档分；输入归属需要仲裁。
- **正式文档**（核心库 `docs/backend/`）还没写：用户在浏览器里怎么打开、怎么看。
