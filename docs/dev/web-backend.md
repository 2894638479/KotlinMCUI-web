# Web 后端

框架跑在 JVM 里，浏览器只做画布。这一页记的是设计思路与实测数据；用户怎么用写在核心库的
`docs/`（正式文档只放核心库），这里不重复。

## 形态

核心把后端拆成两半，这一仓跟着拆：**`WebPlatform`** 是进程那一半（元数据、进程级工具、调度器），
**`WebRootProvider`** 是根那一半（渲染器、输入、屏幕工厂、每输出工具、`frame`）。两半都从服务端状态
取答案的工具由同一个 `WebUtils` 实现（`DslPlatformUtils` + `DslRootUtils`）——拆成两个对象只是把同一批
字段搬来搬去。

多出来的是**帧可以被外部取走**：浏览器按自己的节奏要一帧，provider 把树走一遍、把绘制调用记下来，
交给传输层。所以这里没有窗口、没有渲染循环，也没有任何 Minecraft 类——它不依赖游戏，只依赖核心库。

进程里只发布一个平台（`platformReady` 单次），provider 先注册再发布。所以这个后端要么取代游戏内
渲染，要么由宿主自己决定谁发布。宿主可以是独立 JVM，也可以是游戏内的模组；两种情况下这个后端看到
的世界是一样的。

## 记录器

渲染器实现是**记录**而不是绘制：每个绘制调用追加成一条定长/自描述记录。

- **不做批处理**，所以不需要在作用域切换时 `flush()`。框架自己调的 `flush()` 记为帧末。
- **不求交、不复合变换**：裁剪与变换各记一对 push/pop，客户端按顺序维护自己的栈。做第二遍
  只会多一个出错的地方。
- **资产表跨帧存活**：一个 id 只在首次出现时定义，之后按索引引用。

## 线上格式

一帧就是一维 32 位字数组，`[opcode, payload...]` 重复，浮点走 raw bits。两点是刻意的：

- 记录器写出来的 buffer **就是**载荷，没有第二次编码，也没有两套需要保持一致的结构；
- 帧间补丁退化成字的比较，这才让"每帧做差分"变得便宜。

变长记录（带/不带纹理的 quad、三角形列表、资产定义）把形状写在载荷头几个字里，因此 stride 由
`Op.strideAt` 读出来而不是查表。记录器、报告、SVG 写出器、客户端都走同一个函数——这是格式唯一
的权威定义。

## 三种消息

| 消息 | 什么时候发 | 大小 |
|---|---|---|
| `NOCHANGE` | 与客户端持有的那一帧逐字节相同 | 1 字节 |
| `KEYFRAME` | 第一帧、重连、尺寸变化、客户端基帧不匹配 | 9 + 帧长 × 4 |
| `DELTA` | 其余情况 | 17 + 字面量 × 4 |

补丁**不带后缀**：字面量之后的尾部是客户端已持有的，所以只传前缀长度和一段字面量。这也是补丁
与裁剪/变换栈相容的原因——那些记录和别的记录一样在流里，而客户端是**整份重放**的。

补丁不划算时（字面量接近整帧）直接退回 keyframe。

## 页面栈

框架的屏幕模型是栈：`showScreen` 入栈、关闭出栈。只挂载栈顶，被压住的页保留它声明的 `stable`
状态；**栈底是地板**，关它什么也不做（比留个空白面好）。Esc 是返回键，但它遵守框架自己的规则：
键先给聚焦组件，**没人消费**才出栈。`pop()` 有重入守卫——页面自己的关闭动作会再请求一次出栈。

## 传输层

`gradlew serve -Ppage=<页面> [-Pport=<n>]` 起一个 HTTP + WebSocket 服务；`/` 给页面，`/client.js`
给客户端脚本，`/asset/<id>` 给像素，`/ws` 是帧流与输入。

- **一次渲染、按连接编码**：框架一个进程只有一棵树，所以帧只取一次，然后对每条连接各自编码
  （每条连接持有的基帧不同）后广播。渲染进行中收到的 tick 直接丢弃，不排队。
- **视口是共享的**：根矩形是进程级的，任何一条连接 resize 都会改变所有人的布局，于是所有会话
  的基帧作废、下一帧全部发 keyframe。
- **线程**：所有碰到框架的事都在 `WebUtils.frameExecutor` 这一个线程上；socket 读线程只解析命令
  然后交过去。帧因此只由帧线程写，而捕获请求可能来自别的线程，所以每个会话的写出都走一把锁。
- **资产走 HTTP**：帧里只有 id（一次定义、之后按索引），像素按 id 从 classpath 取——框架自己的
  图标就在 `/assets/kotlinmcui/icon.png`，模组的资产在它自己的 jar 里。`local:` 开头的 id 只有
  本后端描述过的文件才会被服务，客户端报不出任意路径。取不到就是 404，客户端继续画占位框。
- **翻译在服务端**：框架在**构建**树时就要译文，所以 `translate` 直接读 classpath 上的语言文件，
  录进帧里的文字已经是译文，客户端没有键要解。语言是**进程级**的（树只有一棵），因此由第一个
  连上来的客户端决定（它报 `navigator.language`）。
- **`capture` 是唯一的反向成员**：像素在浏览器里，服务端发一条 `capture` 文本命令，客户端
  `canvas.toBlob()` 后用**二进制**回传，服务端写盘并完成那次挂起的调用。导出的是**用户看到的那张
  图**，不是 canvas 的原始内容：canvas 在页面没画到的地方是透明的，而 `toBlob` 不含 CSS 背景，
  所以客户端在重放一帧之前先按页面自己的背景色铺满。那个颜色只写在 `index.html` 里、客户端读回
  来，避免两处各写一遍而漂移。因此 `animation`、`text` 这类大半面积不铺底的页面，拍出来是"背景色
  + 画出来的内容"，而不是一大片透明。
- **输入由服务端翻译**：客户端只转发平台原样（DOM 的 `event.code`、按钮号、修饰键位），框架的
  按键常量在服务端。修饰键位同时写进轮询态——框架判断"按住 shift 的滚轮"用的是
  `isKeyDown(LEFT_SHIFT)`，只看事件上下文不够。
- **滚轮方向**：框架按 GLFW 的方向计数（正值向上），所以两个轴都要取负；带横向增量的事件
  （触控板，或浏览器替我们交换了轴）直接走横向滚动条。

## 边界：一个客户端

alpha 期这个后端**按单客户端设计**。多连接能工作，但不是被支持的能力，而且后果是可观察的：

- **视口是共享的**：根矩形是进程级的，两条窗口尺寸不同的连接会互相把对方的基帧作废，于是每一帧
  都是 keyframe，**帧复用彻底失效**——静止页面从 1 字节退回整帧。按尺寸档分组是唯一的解法。
- **语言是共享的**：树只有一棵，语言在构建期决定，所以**第一个**连上来的客户端决定所有人的界面
  语言，后到的客户端报什么都没用。
- **输入没有归属**：两个鼠标都能操作同一个页面栈，包括用 Esc 出栈。

这不是缺陷登记，而是**当前公开面的边界**：宿主若要服务多个客户端，得自己做尺寸、语言与输入的
仲裁，或者等后端按尺寸档分组。

## 帧的节奏

客户端用 `requestAnimationFrame` 拉帧，也就是**跟着设备刷新率**走。这刻意不是 `setTimeout` 循环：
一收到帧就立刻再要一帧会把服务端的帧线程压到几百帧每秒，那些帧又和用户等待的输入抢同一个线程
——页面能报出四五百 fps 却依然顿，就是这么来的。代价是：

- 帧在变（动画、悬停、提示）时每个刷新周期要一帧；上一帧没有变化就降到 120 ms 轮询一次，
  静止页面几乎不耗。
- 输入到达立刻置位，下一次刷新就发出去（延迟上限一个刷新周期）。
- 叠层关闭后这个节奏才成立：调试叠层每帧都改数字，等于永远"有变化"。

## 字体度量

排版在服务端，字体在浏览器，所以**度量由客户端上报**：连接时量一批码点，之后每遇到没量过的字
就补报一次（服务端合并），布局下一帧就正确。这样既不用发字体文件，也不用赌两边字体一致；对
非拉丁文字尤其重要——第一版中文页面字形叠在一起，就是因为固定采样里没有那些码点。客户端没有
上报之前，`WebFont` 的近似表兜底（宽文字按一个 em 算，避免挤在一起）。

## 实测

`gradlew measure -Ppage=<页面> -Pframes=<n> [-Psvg=<文件>]` 录真实演示页。下表是 **2026-10-17**、
`-Pframes=30`、1280×720、翻译生效、叠层关闭下的**一次连续测量**——九页在同一轮里跑完，所以行与行
可比。两个前提要说清。一是页面来自核心 jar，**换核心 jar 就该重测**：下表在**三份**核心 jar 构建上
给出逐行一致的结果——`1132456 B`(01:08) → `1132583 B`(01:45) → `1133015 B`(01:58,
sha256 `764d244f…`)，其中最后一次是在**已知 jar 完全没变**的前提下跑完的（开跑前与结束后各校验一次，
size 与 sha256 相同），另两轮与它逐行一致。二是 web 仓这边测得于 `1d12ff9`，此后只有客户端脚本、
测试与文档变动，都不参与 `measure`。

| 页面 | 冷帧 | 稳态 | 相同帧 | 冷帧 flush | 字数构成 |
|---|---|---|---|---|---|
| entry | 4164 B | 4076 B | 28/29 | 20 | text 88% / button 4% |
| color | 6144 B | 6144 B | 29/29 | 32 | quad 65% / text 22% |
| render | 20692 B | 20180 B | 28/29 | 38 | text 66% / quad 27% |
| transform | 1620 B | 1620 B | 29/29 | 5 | text 64% / quad 22% |
| text | 14600 B | 14600 B | 29/29 | 8 | text 98% |
| scroll | 13088 B | 13088 B | 28/29 | 80 | text 88% / button 8% |
| animation | 208 B | 252 B | 0/29 | 3 | text 69% / button 13% |
| layout | 8260 B | 8260 B | 29/29 | 39 | text 89% / quad 6% |
| image | 5404 B | 5404 B | 29/29 | 40 | text 49% / quad 34% |

「冷帧」与「稳态」是两列而不是一列，因为它们不是一回事：静态页面两者相等，而 `animation` 冷帧
208 B、稳态 252 B——同一列里混放两种口径会让行与行不可比。`flush` 记的是**冷帧（第 0 帧）里的
`Op.FLUSH` 记录数**，也就是框架这一帧要求中断批次几次；它不是每帧平均，`-Pframes` 也不影响它
（`animation` 每帧都在变、`相同帧` 是 0/29，所以它的每帧 flush 数这份报告不暴露）。

四点结论：

1. **同帧短路是主要收益**：九页里七页稳态每帧只花 1 字节。
2. **前后缀补丁对"变化帧"有效**（`animation` 平均 47 B 对整帧 252 B，29 个变化帧**没有一个退化成
   keyframe**），但树结构一变就退化：`scroll` 那一个变化帧要传 2706 个字面量（整帧 3272 词），
   `render` 是 1602 / 5045。需要时再上分块差分。
3. **文字是最大开销**（49%–98%，多数页在 64% 以上）：合并成 run 是下一个杠杆。
4. **拍照保真要看透明占比**：`-Pcapture` 的产物在补上背景铺底之前，`animation` 有 97.9%、`text`
   有 87.3% 的面积是透明的（看着像白屏），补上之后两页都是 0%，而本来就自己铺满背景的 `render`
   保持 0% 不变——它就是这一条的对照组。

报告里还有一列 `first difference`：帧在变时告诉你是哪条记录先变的（对 text 会打出那个字和它所在的
文字串）。第一次踩到"静止页永远在变"就是靠它定位到调试叠层的耗时数字。

## 未决

- **四角颜色不构成仿射关系时会有一条对角缝**：canvas 2D 没有重心渐变，客户端按框架的模型把这样的
  四边形拆成两个三角形，每个三角形用一张 16×16 的缓存色场做仿射插值并裁剪到三角形内；三角形列表
  则逐三角形插值。仿射相关的四角是精确的，而两个各自拟合的平面在公共对角线上不相等，所以调色板
  方块上能看见一条一像素的暗缝。可选细分，或想办法让两个三角形共用一个双线性场。
- **文字合并成 run**：格式加一条 run 记录（样式 + 逐字符 x），把 36 B/字符降到 8–12 B。
- **物品与原版贴图**：`minecraft:` 开头的 id 会去 `gameDir` 下的 `versions/*/*.jar` 与
  `mods/*.jar` 里找（`-PgameDir` 指定安装目录），找不到就是占位框。没有真实安装时全部落到占位，
  这是设计而不是缺陷——本库不随附游戏资源。另外页面若没有指名任何本地图片（核心的演示页默认就是
  空串），后端会收到空 id 并记一条警告，照样画占位框。
- **分块差分**：等有真实交互数据，看前后缀退化的频率再决定。
- **反向成员**：`clipboard`/`openUri`/`narrate`/`playButtonSound` 还要反向消息；`capture` 已完成。
- **多客户端**：见上面「边界：一个客户端」——按尺寸档分组、语言与输入仲裁都还没做，alpha 期不承诺。
- **正式文档**（核心库 `docs/backend/`）还没写：用户在浏览器里怎么打开、怎么看。
- **外部根承载框架页面要走挂载路径**：`isFocused`/`isHovered` 对"没有根状态的树"会**抛错**（静默替主根
  回答更糟），而框架页面在 **build 期**就读焦点（调色板编辑器、布局页都是）。所以前提是：用
  `DslRuntime.createRoot(provider, …)` 拿根，**再把屏 `collect` 进去** —— `collect` 会把根状态盖到该屏的
  store 上，之后 build 才读得到。**手写一个 `DslScope` 直接挂屏不行**：它的 children 是普通 group，不盖章。
  曾经有一条标记为"故意红"的用例钉这件事，后来查明**红的原因是用例没走这条路、不是能力缺失** ——
  "它红过"与"它做不到"在失败测试里长得一模一样，这条区别记在这里。
- **preedit 已有判据**：`globalPreedit(info)` 是 `DslScope` 的公开成员，沿**调用它的那棵树**派发 ⇒ 两条根
  各挂一个记录用的探针，断言"只到它自己那棵"，已绿。
- **hover 的判据要嵌套一层**：`DslRootComponent.render()` 在 hover 相位**之前**会
  `children.forEach { it.rect copyFrom rect }`，所以**根的直接子组件恒等于全屏** —— 两个同样大小的根会
  同时命中，这是**正确行为**。要按几何区分，探针必须放在**容器里面**（容器是直接子、探针保留自己的
  rect），并先给记录器一个真实表面尺寸。曾按直接子写过一版，红的原因是这条、不是能力缺失，已撤掉，
  等嵌套探针进来再补。

## 迁移：平台拆分之后

- **常见坑**：`DslRootProvider` **不需要**实现 `DslBackendRenderer`。`frame()` 里用
  `context(renderer, renderParam, input.mouse) { root.component.render() }` 把 `renderer` 当
  **context 实参**传进去；**不要 `by Renderer` 让 provider 冒充 renderer**——那会把两个角色的生命周期
  绑在一起，而 provider 本来就允许被多个根共享。
- **`renderer == null` 不等于"不画"**：渲染器**同时是字体来源**（文字组件通过
  `context(backend: DslBackendRenderer<RP>) { backend.getFont(...) }` 取字形）。把 `renderer` 设成
  `null` 会**连字体一起拿掉**。本仓渲染器恒非空；将来若做"无绘制订阅根"，不要用 `null` 表达它。
- **换核心之后要重建所有后端产物**：`run/mods` 里任何按旧核心编译的 jar 都会在启动时炸成
  `NoClassDefFoundError`（聚合 backend 已删）。这不是新代码坏了，是旧产物没重建——先重建再判断。
- **尺寸归驱动方**，不归 provider：provider 的职责是每帧**把 rect 写出去**，来源不归契约管。web 的
  尺寸来自客户端画布，所以记在记录器上、由驱动方在调 `frame` 之前写入。
