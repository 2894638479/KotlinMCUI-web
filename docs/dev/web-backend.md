# Web 后端

框架跑在 JVM 里，浏览器只做画布。这一页记的是设计思路与实测数据；用户怎么用写在核心库的
`docs/`（正式文档只放核心库），这里不重复。

## 形态

核心不再有"平台对象"这一层：元数据由 `DslRuntime.install { WebMetadata }` 安装，进程级工具由
`DslRuntime.start { WebUtils }`（`() -> DslPlatformUtils`）发布，`dslUtils` 就是这个工具的入口。
**根那一半**是本仓自己构造的 `DslRoot`（渲染器 `Recorder`、输入 `WebInput`、屏幕工厂
`WebScreenFactory`）；同一个 `WebUtils` 同时实现 `DslPlatformUtils` 与 `DslRootUtils`——两组工具都
从服务端状态取答案，拆成两个对象只是把同一批字段搬来搬去。

多出来的是**帧可以被外部取走**：浏览器按自己的节奏要一帧，`WebBackend.frame()` 把树走一遍、把绘制
调用记下来，交给传输层。所以这里没有窗口、没有渲染循环，也没有任何 Minecraft 类——它不依赖游戏，
只依赖核心库。

进程里只发布一份工具（`DslRuntime.start` 只认第一个发布者），**没有 provider 注册这一步**：根由后端
自己构造，不做注册。所以这个后端要么取代游戏内渲染，要么由宿主自己决定谁发布。宿主可以是独立
JVM，也可以是游戏内的模组；两种情况下这个后端看到的世界是一样的。

## 记录器

渲染器实现是**记录**而不是绘制：每个绘制调用追加成一条定长/自描述记录。

- **不做批处理**，所以不需要在作用域切换时 `flush()`。记录器自己的 `flush()` 在帧末追加 `Op.FLUSH`，它不是框架接口。
- **不复合变换**：变换按 push/pop 记录，客户端按顺序维护自己的矩阵栈。裁剪不同：矩形按**调用时的局部坐标**记录，客户端在重放 `CLIP_PUSH` 时用当时完整的变换投影四个角并做精确交集。
- **资产表跨帧存活**：一个 id 只在首次出现时定义，之后按索引引用。

### 裁剪作用域

`withScissor(rect, block)` 的 `rect` 是**当前局部坐标**。记录器进入作用域时先把四条边快照下来（`Rect` 只借用，可能是会被改写的 `MutRect`），然后保证每个作用域恰好写出一条 `CLIP_PUSH` / `CLIP_POP`。即使矩形未测量、非有限、宽高非正或方向相反，也会写一条**零面积哨兵**；块仍然执行恰好一次，块里记录的绘制也仍在帧里，只是回放时没有覆盖。`withTransform` 同理：push/pop 在 `finally` 中成对写出，块抛异常也不会让下一帧的裁剪或变换栈错位，原异常原样继续传播。

客户端在 `CLIP_PUSH` 时用**进入该作用域时**的完整变换（包含外层变换与投影）把矩形四角映射到输出空间：四条边必须有限且宽高为正，当前变换必须有限且可逆，四个角的 `w` 必须大于 0；满足时裁剪区域是已有裁剪与该**投影四边形**的精确交集（Canvas 原生 `clip()`，不以包围盒代替），否则保存并裁到空路径。裁剪一旦建立就在输出空间冻结，块内后续的变换不会移动它。`CLIP_POP` 是无条件恢复，所以无效 push 也必须有配对的 save/restore，否则会吃掉外层裁剪；这是“跳过 push 却照常 pop”会破坏嵌套的原因。裁剪只限制覆盖：颜色场、UV、预乘混合与绘制顺序都不变。逐像素场仍先画到复用离屏缓冲，再一次性 `drawImage` 合成，屏幕裁剪在最终合成处生效；文字、控件、物品与三角形都走同一套屏幕裁剪。

## 图元输入

`Recorder` 实现了核心的四个类型化图元入口，取代了原先可空的格式参数：

- quad 有两种：纯颜色 `renderQuad(rect, 四角颜色)`，带纹理 `renderQuad(..., image, uv)`。后者
  `image` 与 `uv` 都不可空，所以"给了 uv 却没有图"这种中间态在类型上就不存在。
- 三角形有两种：每个顶点 `x, y`（stride 2），或每个顶点 `x, y, u, v`（stride 4，带 `image`）。
- `vertices` / `colors` 是 `MeasureArray` / `ColorArray`，只在本次调用期间借用。

校验顺序是契约的一部分：

1. **结构**。设 `N = colors.size`：要求 `N % 3 == 0`，且 `vertices.size` 恰好等于 `stride * N`
   ——用除法与取余判定，判定本身不会乘法溢出。不满足就抛 `IllegalArgumentException`，
   **发生在任何资源查找与写入之前**，即使 `image` 为空也一样。两个数组都空是合法的空操作。
2. **数值**。每个坐标、UV 与目标矩形都必须是已测量、有限、且转换后仍是有限 `Float` 的 `Measure`；
   目标矩形宽高必须为正，纹理图的标称尺寸也必须有限且为正。任何一处不合格（包括最后一个顶点或
   UV）都跳过**整个**调用，不留下半条记录。UV 为负或超出图像范围是合法的，不夹取、不换行。
3. **资源**。`source == null` 的 holder 什么都不画，也不定义资产。非空 holder 即使标识符是空串
   也保持纹理 stride，并引用显式的缺失 id `kotlinmcuiweb:missing`；它绝不会退化成无纹理图元。
   每条带纹理记录还携带**本次绘制**的名义宽高，因此同一个 asset id 可以在同一帧里以不同的名义
   尺寸被采样。

记录器同步写字，所以借来的 `Rect` / `MeasureArray` / `ColorArray` 在返回前已经复制进帧；调用方
随后改写这些对象不会改变已录下的帧。

浏览器侧按自己的资产缓存判定就绪：加载中（`null`）不画；加载成功用真实像素；确认失败（404、
不支持的来源、坏标识符、无法 percent-encode 的标识符等）缓存一张真正的检查板纹理，并沿原来的几何、
UV、名义尺寸与顶点色采样。缺失纹理不会被纯色、灰色矩形或无纹理图元替代，三角形与四边形都走纹理路径。
采样按图片自身的像素周期重复：UV 为负或超出名义尺寸时取模回图像内，而不是留白。单色 tint 的
路径用 CanvasPattern 的 `repeat`，一次 fill 覆盖整段 UV，所以再大的 UV 跨度也不会变成逐个 tile 的
循环；逐像素路径对每个样本做同样的取模。`ImageHolder.empty` 仍是"没有图像"，不猜测失败原因。

### 颜色场

quad 的四个角（LT、RT、LB、RB）在**原始未变换的 Rect** 的局部坐标里定义一个双线性场：
`u=(x-left)/width`、`v=(y-top)/height`，权重 `(1-u)(1-v)`、`u(1-v)`、`(1-u)v`、`uv`。三角形用三个顶点
的重心权重。两种场的规则相同：把 wire 上的 straight sRGB 分量与 alpha 归一化到 0..1，**先在每个角把
RGB 乘以 alpha**，再在浮点里插值预乘 RGB 与 alpha；不做线性光/Oklab 转换，也不在中间量化到 8 位。所以
一个角 alpha 为 0 时它隐藏的 RGB 不参与，alpha 很小的插值也不会被 unpremultiply 放大。

浏览器侧对这套场的处理分两条路，但**最终都只在屏幕上做一次 `source-over`**：

- **单色 tint + 仿射纹理**仍走 CanvasPattern：一次 fill，必要时在复用的离屏表面上用该资源的不透明
  RGB 副本做 `multiply`/`destination-in` 施加 tint 与 alpha。`multiply` 只有目标不透明时才等于乘法，
  所以先复制成不透明 RGB、再用原纹理和 tint alpha 把 alpha 放回去；这避免了在屏幕目的地上改掉已画
  好的界面，也避免 alpha 被平方或把背景混进 RGB。白色不透明 tint 直接一次 `source-over`。
- **顶点色不同、或变换含透视**时，逐可见像素计算预乘源色，再转换为直通 RGBA `ImageData` 写进复用的离屏画布，
  再以一次 `source-over` 合成。设备像素先通过**逆 homography** 回到原始局部坐标，因此旋转、错切和
  正 w 的透视都采样同一个源局部场，而不是投影包围盒或两个各自拟合的仿射三角形。裁剪只限制最终
  覆盖，不改变场的局部坐标；重复/裁剪的 UV 只改变纹素，不会重启或缩放颜色场。
- 几何上仍可以理解为两个三角形，但它们不参与着色：每个设备采样只被覆盖一次，公共对角线上没有
  两个平面或两次合成，所以不会出现对角缝、折痕或双倍 alpha。

带纹理时，源的预乘 RGB 是 `插值后的预乘顶点 RGB × 纹素 straight RGB × 纹素 alpha`，alpha 是
`插值后的顶点 alpha × 纹素 alpha`，两个因子各乘一次。纹理 UV/名义尺寸与颜色场互相独立。纹素按最近
邻采样并按图片自身周期重复，负 UV 与超出名义尺寸的 UV 都合法。

离屏缓冲只覆盖当前画布的可见范围并复用：每个资源只读一次像素、只建一份不透明 RGB 副本，没有按
tint 复制整图的缓存，也没有逐绘制的全尺寸分配。代价是透视/变化顶点色的绘制在 JS 里逐像素计算；
单色 tint 的纹理与单色 quad 仍走 Canvas 的快速路径。

三角形列表先识别共享边，再决定覆盖率：共享边按像素中心只归一侧，外沿按像素与边界的交面积抗锯齿。
面积有意重叠的三角形仍按列表顺序合成，颜色与 UV 各自保持原局部三角形的重心场。

### 测试模型

`src/test/js/primitive-input.test.cjs` 用 VM 执行实际发布的 `client.js`，其中的 Canvas 桩按规范实现了
`source-over`/`multiply`/`destination-in`、仿射采样、repeat pattern、`createImageData`/`putImageData`
（含 dirty rectangle）与 `drawImage`；断言读取真实绘制的**像素**，并与测试内独立计算的预乘权重公式
比较。它仍是模型而不是浏览器：平滑、亚像素边缘覆盖与浏览器色彩管理都没有建模，真实浏览器验收应看
Chrome 截图或浏览器一致性页。裁剪用例另用真实路径检查投影四边形、嵌套 push/pop 配对和空裁剪语义；
文字在模型里只画一个确定的矩形作为字形替身，不声称字形形状。

`src/test/js/clip-acceptance.html` 与 `clip-acceptance.js` 是可移植的浏览器夹具：它加载**实际发布的**
`client.js`，只替换 WebSocket，帧通过真实的 KEYFRAME 解码进入生产绘制路径，断言读取真实 Canvas 像素。
Node 测试会在本机安装的 headless Chrome 中运行它，覆盖 45° 菱形、投影/仿射嵌套、内层变换冻结、
空/不相交/非法作用域与 POP 后恢复、纹理/渐变/多 alpha 层以及文字/控件/物品边界。它只证明这一版
本机 Chromium 的行为，不代表所有浏览器；SVG 快照仍是诊断近似，不是像素级参考。


## 线上格式

一帧就是一维 32 位字数组，`[opcode, payload...]` 重复，浮点走 raw bits。两点是刻意的：

- 记录器写出来的 buffer **就是**载荷，没有第二次编码，也没有两套需要保持一致的结构；
- 帧间补丁退化成字的比较，这才让"每帧做差分"变得便宜。

变长记录（带/不带纹理的 quad、三角形列表、资产定义）把形状写在载荷头几个字里，因此 stride 由
`Op.strideAt` 读出来而不是查表。记录器、报告、SVG 写出器、客户端都走同一个函数——这是格式唯一
的权威定义。

带纹理记录在 UV 之后追加两个 Float 字（名义宽、名义高）；带纹理三角形把它们放在颜色之后。没有
旧格式兼容层：客户端直接用本次绘制的名义尺寸把 UV 缩放到自己实际持有的像素（真实图片或检查板），
所以同一 id 不同名义尺寸也能保持各自采样矩形。`FrameStream` 仍只搬运 32 位字，不解释记录形状。

## 三种消息

| 消息 | 什么时候发 | 大小 |
|---|---|---|
| `NOCHANGE` | 与客户端持有的那一帧逐字节相同 | 1 字节 |
| `KEYFRAME` | 第一帧、重连、尺寸变化、客户端基帧不匹配 | 9 + 帧长 × 4 |
| `DELTA` | 其余情况 | 17 + 字面量 × 4 |

补丁**不带后缀**：字面量之后的尾部是客户端已持有的，所以只传前缀长度和一段字面量。这也是补丁
与裁剪/变换栈相容的原因——那些记录和别的记录一样在流里，而客户端是**整份重放**的。

补丁不划算时（字面量接近整帧）直接退回 keyframe。

## 页面栈

框架的屏幕模型是栈：`showScreen` 入栈、关闭出栈。只挂载栈顶，被压住的页保留它声明的 `stable`
状态；**栈底是地板**，关它什么也不做（比留个空白面好）。Esc 是返回键，但它遵守框架自己的规则：
键先给聚焦组件，**没人消费**才出栈。`pop()` 有重入守卫——页面自己的关闭动作会再请求一次出栈。

## 传输层

`gradlew serve -Ppage=<页面> [-Pport=<n>]` 起一个 HTTP + WebSocket 服务；`/` 给页面，`/client.js`
给客户端脚本，`/asset/<id>` 给像素，`/ws` 是帧流与输入。

- **一次渲染、按连接编码**：框架一个进程只有一棵树，所以帧只取一次，然后对每条连接各自编码
  （每条连接持有的基帧不同）后广播。渲染进行中收到的 tick 直接丢弃，不排队。
- **视口是共享的**：根矩形是进程级的，任何一条连接 resize 都会改变所有人的布局，于是所有会话
  的基帧作废、下一帧全部发 keyframe。
- **线程**：所有碰到框架的事都在 `WebUtils.frameExecutor` 这一个线程上；socket 读线程只解析命令
  然后交过去。帧因此只由帧线程写，而捕获请求可能来自别的线程，所以每个会话的写出都走一把锁。
- **拆除顺序**：`stop()` 先 `root.close()`，再关 server 与会话，最后把页面释放交给帧线程并等它
  做完。根先关，是因为"一帧在飞"时断开必须失败在根的门上——`IllegalStateException` 说的是根关了，
  而不是让那一帧继续画进没人看的树、或把它报成页面的 `was released`（那是页面的问题，不是输出
  已经结束）。页面释放要放在帧线程上，因为它们 dispose 的 life scope 协程就跑在那一线程。
  根的门**不负责停线程**：帧线程是进程级的守护线程，`stop()` 只把它排空，不关它；页面在根关掉后
  不再从根上注销（根已经没了），所以 `unmount` 对已关的根是空操作。
- **资产走 HTTP**：帧里只有 id（一次定义、之后按索引），像素按 id 从 classpath 取——框架自己的
  图标就在 `/assets/kotlinmcui/icon.png`，模组的资产在它自己的 jar 里。`local:` 开头的 id 只有
  本后端描述过的文件才会被服务，客户端报不出任意路径。取不到就是 404，客户端把它记成已确认失败，
  用同一几何/UV/名义尺寸采样缓存的检查板缺图纹理，而不是画色块。
- **翻译在服务端**：框架在**构建**树时就要译文，所以 `translate` 直接读 classpath 上的语言文件，
  录进帧里的文字已经是译文，客户端没有键要解。语言是**进程级**的（树只有一棵），因此由第一个
  连上来的客户端决定（它报 `navigator.language`）。
- **`capture` 是唯一的反向成员**：像素在浏览器里，服务端发一条 `capture` 文本命令，客户端
  `canvas.toBlob()` 后用**二进制**回传，服务端写盘并完成那次挂起的调用。导出的是**用户看到的那张
  图**，不是 canvas 的原始内容：canvas 在页面没画到的地方是透明的，而 `toBlob` 不含 CSS 背景，
  所以客户端在重放一帧之前先按页面自己的背景色铺满。那个颜色只写在 `index.html` 里、客户端读回
  来，避免两处各写一遍而漂移。因此 `animation`、`text` 这类大半面积不铺底的页面，拍出来是"背景色
  + 画出来的内容"，而不是一大片透明。
- **输入由服务端翻译**：客户端只转发平台原样（DOM 的 `event.code`、按钮号、修饰键位），框架的
  按键常量在服务端。修饰键位同时写进轮询态——框架判断"按住 shift 的滚轮"用的是
  `isKeyDown(LEFT_SHIFT)`，只看事件上下文不够。
- **滚轮方向**：框架按 GLFW 的方向计数（正值向上），所以两个轴都要取负；带横向增量的事件
  （触控板，或浏览器替我们交换了轴）直接走横向滚动条。

## 本地图片

`localImage` 跑在帧线程上，契约（`DslPlatformUtils` 的 KDoc）禁止这些方法等 io，所以这里只查缓存，
**帧线程从不读盘**：

- 缓存是 `id → { file, lastUsed, holderOrNull }`，`holderOrNull == null` 表示"尺寸正在后台读"。
  未命中时先登记条目、把 `ImageIO.read` 丢给 `Dispatchers.IO`，**立即返回 `ImageHolder.empty`**
  （"还没到"就是 `ImageHolder` 约定的"不画"）；读完把答案**投回帧线程**才写缓存，下一次调用起就有
  尺寸。缓存只有帧线程改，所以是普通 `HashMap`，不是并发容器。
- 读失败也记成空 holder 并只警告一次（否则每帧都会重开同一个坏文件）；`reloadLocalImage` 连失败记录
  一起丢，下次重新读。
- 淘汰：每帧 `sweepLocalImages()` 一次（帧就是后端的时钟，不另起定时器），超过
  `LOCAL_IMAGE_TTL_MILLIS`（60 秒）没被问过的条目丢掉。页面还在画它就会在建帧时刷新 `lastUsed`，
  所以被淘汰的只会是页面已经不要的图。
- `Dispatchers.IO` 是守护线程，所以 headless 的 `measure`、停下来的 `serve` 不会因为一次没读完的
  图片挂着不退出。
- **线上字节不受影响**：淘汰只决定**以后**的 `localImage` 要不要重新读，不改变已经录下的帧；演示页
  默认没有本地图片（空串，见「未决」），所以 `text` 冷帧 14572 B / 14581 B wire、`image` 冷帧
  5248 B / 5257 B wire；这些默认页面不会触发本地图片缓存的重新加载。

## 边界：一个客户端

alpha 期这个后端**按单客户端设计**。多连接能工作，但不是被支持的能力，而且后果是可观察的：

- **视口是共享的**：根矩形是进程级的，两条窗口尺寸不同的连接会互相把对方的基帧作废，于是每一帧
  都是 keyframe，**帧复用彻底失效**——静止页面从 1 字节退回整帧。按尺寸档分组是唯一的解法。
- **语言是共享的**：树只有一棵，语言在构建期决定，所以**第一个**连上来的客户端决定所有人的界面
  语言，后到的客户端报什么都没用。
- **输入没有归属**：两个鼠标都能操作同一个页面栈，包括用 Esc 出栈。

这不是缺陷登记，而是**当前公开面的边界**：宿主若要服务多个客户端，得自己做尺寸、语言与输入的
仲裁，或者等后端按尺寸档分组。

## 帧的节奏

客户端用 `requestAnimationFrame` 拉帧，也就是**跟着设备刷新率**走。这刻意不是 `setTimeout` 循环：
一收到帧就立刻再要一帧会把服务端的帧线程压到几百帧每秒，那些帧又和用户等待的输入抢同一个线程
——页面能报出四五百 fps 却依然顿，就是这么来的。代价是：

- 帧在变（动画、悬停、提示）时每个刷新周期要一帧；上一帧没有变化就降到 120 ms 轮询一次，
  静止页面几乎不耗。
- 输入到达立刻置位，下一次刷新就发出去（延迟上限一个刷新周期）。
- 叠层关闭后这个节奏才成立：调试叠层每帧都改数字，等于永远"有变化"。

## 字体度量

排版在服务端，字体在浏览器，所以**度量由客户端上报**：连接时量一批码点，之后每遇到没量过的字
就补报一次（服务端合并），布局下一帧就正确。这样既不用发字体文件，也不用赌两边字体一致；对
非拉丁文字尤其重要——第一版中文页面字形叠在一起，就是因为固定采样里没有那些码点。客户端没有
上报之前，`WebFont` 的近似表兜底（宽文字按一个 em 算，避免挤在一起）。

## 实测

`gradlew measure -Ppage=<页面> -Pframes=<n> [-Psvg=<文件>]` 录真实演示页。`-Psvg` 写出的是**诊断快照**：
纹理是检查板标记，四角/三顶点的颜色场用粗网格近似，两者都不是像素级参考；以浏览器客户端为准。
裁剪在 SVG 里写成投影四边形的 `<clipPath>`（不是包围盒）；客户端会判为空的裁剪（未测量、非有限、
反向、奇异变换或穿过视平面）在这里是**空 clipPath**，不会退回“不裁剪”。颜色仍按粗网格取样，
纹理仍没有像素，所以这张图只能用来检查几何、层级和裁剪形状。
下表是 `-Pframes=30`、
1280×720、翻译生效、叠层关闭下的九页测量。2026-10-29 使用同一份核心 jar 逐页重测；
字节数来自记录器的真实缓冲区，wire 大小来自实际编码消息。核心或页面变化后需要重新测量。

| 页面 | 冷帧 | 稳态 | 相同帧 | 字数构成 |
|---|---|---|---|---|
| entry | 6104 B | 6016 B | 28/29 | text 93% / button 2% |
| color | 6020 B | 6020 B | 29/29 | quad 66% / text 22% |
| render | 20544 B | 20032 B | 28/29 | text 67% / quad 27% |
| transform | 1604 B | 1604 B | 29/29 | text 65% / quad 22% |
| text | 14572 B | 14572 B | 29/29 | text 98% / quad 1% |
| scroll | 12772 B | 12772 B | 28/29 | text 90% / button 8% |
| animation | 200 B | 244 B | 0/29 | text 72% / button 14% |
| layout | 8108 B | 8108 B | 29/29 | text 91% / quad 6% |
| image | 5248 B | 5248 B | 29/29 | text 51% / quad 35% |

「冷帧」与「稳态」是两列而不是一列，因为它们不是一回事：静态页面两者相等，而 `animation` 冷帧
200 B、稳态 244 B——同一列里混放两种口径会让行与行不可比。已移除旧的框架 flush 计数：当前 `Op.FLUSH` 仅为记录器的帧末标记，不能用它推断 GPU 批次。

四点结论：

1. **同帧短路是主要收益**：五页 29/29 完全相同，另三页（`entry`/`render`/`scroll`）只在窗口里那
   一次变化时付一次 delta，稳态据此每帧只花 1 字节；只有 `animation` 每帧都在变。
2. **前后缀补丁对变化帧有效**：`animation` 的 29 个变化帧平均 47 B，整帧为 244 B，
   没有退化为 keyframe。结构变化仍可使补丁接近整帧：`scroll` 为 2637 / 3193 个词，
   `render` 为 1579 / 5008 个词；是否需要分块差分应依据真实交互数据。
3. **文字占主要空间**：九页里八页以 `text` 为主，占 51%–98%；`color` 以 `quad` 为主，占 66%。
   字形 run 编码仍有压缩空间。
4. **传输大小与截图正确性需要分别验收**：这份报告测命令与编码字节，不验证浏览器绘制后的透明度、
   字形与合成结果。JS 用例现在用一个按 Canvas 规范实现的小模型校验合成后的像素（颜色与 alpha），
   但模型不是浏览器，真实验收仍应看截图与最终颜色，不能根据命令统计推断。

报告里还有一列 `first difference`：帧在变时告诉你是哪条记录先变的（对 text 会打出那个字和它所在的
文字串）。第一次踩到"静止页永远在变"就是靠它定位到调试叠层的耗时数字。

## 未决

- **逐像素场的边缘覆盖是二值的**：非单色或透视的绘制按像素中心决定覆盖，不做亚像素抗锯齿；相邻
  同色块的边界因此不会有半像素混合。内部采样与重叠覆盖已由单一颜色场保证不裂不重，边缘 AA 仍可另做。
- **文字合并成 run**：格式加一条 run 记录（样式 + 逐字符 x），把 36 B/字符降到 8–12 B。
- **物品与原版贴图**：`minecraft:` 开头的 id 会去 `gameDir` 下的 `versions/*/*.jar` 与
  `mods/*.jar` 里找（`-PgameDir` 指定安装目录），找不到就由客户端画检查板缺图纹理。没有真实安装
  时全部落到缺图纹理，这是设计而不是缺陷——本库不随附游戏资源。另外页面若没有指名任何资源图片
  （核心的演示页默认就是空串），后端会把它当作"非空 holder 的空标识符"，按
  `kotlinmcuiweb:missing` 记一条纹理引用；客户端取不到像素就沿原参数采样检查板。注意本地文件
  provider **读失败仍返回 `ImageHolder.empty`**，按"没有图像"处理、不画；这与非空 holder 在客户端
  确认 404 的失败路径不同，都是契约规定的行为。
- **单色 tint 的纹理仍用仿射 pattern**：这条快速路径只用于仿射变换（`m20=m21=0,m22=1`）；含透视的
  绘制统一走逐像素场，UV 由逆 homography 逐样本恢复。若将来给 pattern 加透视，需要单独验证采样与
  重复语义，不能直接复用仿射结论。
- **需要读像素的边界**：单色 tint 的 `multiply` 路径依赖该资源的不透明 RGB 副本；逐像素路径依赖
  纹理的 straight RGBA。两者都只读一次、按资源缓存。浏览器拒绝读像素时（跨源 taint 等），不透明副本
  退回原图（alpha 仍精确，半透明纹素的 RGB 会带一点背景），逐像素路径则跳过该绘制而不是猜测像素。
  服务端只提供同源 `/asset/`，正常路径不会触发 taint。离屏缓冲只覆盖当前可见范围并复用；每个资源只
  保留一份副本，不按 tint 复制整图。
- **分块差分**：等有真实交互数据，看前后缀退化的频率再决定。
- **反向成员**：`clipboard`/`openUri`/`narrate`/`playButtonSound` 还要反向消息；`capture` 已完成。
- **多客户端**：见上面「边界：一个客户端」——按尺寸档分组、语言与输入仲裁都还没做，alpha 期不承诺。
- **正式文档**（核心库 `docs/backend/`）还没写：用户在浏览器里怎么打开、怎么看。
- **外部根承载框架页面走 `DslRoot` 的挂载路径**：`isFocused`/`isHovered` 对"没有根状态的树"会**抛错**
  （静默替主根回答更糟），而框架页面在 **build 期**就读焦点（调色板编辑器、布局页都是）。所以前提是：
  用公开构造器 `DslRoot(输入, 渲染器, 屏幕工厂, 根工具)` 建根，**再把屏 `collect` 进去** —— `collect`
  会把根状态盖到该屏的 store 上，之后 build 才读得到。**手写一个 `DslScope` 直接挂屏不行**：它的
  children 是普通 group，不盖章。曾经有一条标记为"故意红"的用例钉这件事，后来查明**红的原因是用例
  没走这条路、不是能力缺失** —— "它红过"与"它做不到"在失败测试里长得一模一样，这条区别记在这里。
- **preedit 已有判据**：`globalPreedit(info)` 是 `DslScope` 的公开成员，沿**调用它的那棵树**派发 ⇒ 两条根
  各挂一个记录用的探针，断言"只到它自己那棵"，已绿。
- **hover 已按"嵌套探针"写成**：`DslRootComponent.render()` 在 hover 相位**之前**会
  `children.forEach { it.rect copyFrom rect }`，所以**根的直接子组件恒等于全屏** —— 在那一层写会让两个
  同尺寸的根都 hover（正确行为，但判据失效）。判据把探针放进**容器**（容器是直接子、探针保留自己的
  rect），并**先给记录器一个真实表面尺寸**（否则根 rect 退化成 0x0）。断言是"指针落 A 的探针 ⇒ A 收到、
  **B 永远不会被告知 A 的 id**"；注意 `setHovered(null)` **即使值没变也会派发**，所以 B 的正确期望是
  "只听到 null"，不是"什么都没收到"。**证伪已实测**：把帧打在所有者根上 ⇒ A 收不到 ⇒ 必红。
- **通知契约（写判据前先看这条）**：`setFocus` 与 `setHovered` **无条件广播** —— `DslRootState.setHovered`
  的 KDoc 明写它与渲染遍历一致：**每帧重写 hover，而不是只在身份变化时通知**；
  `noteKeyboardNarration`/`noteMouseNarration` **去重**（同一句不重复播报）；`setPreedit` **无通知**。
  ⇒ **hover 是电平式、不是边沿式**，任何"只在变化时才通知"的断言都是错的（我写过一版，红在一个正确的
  行为上）。

## 迁移：平台拆分之后

- **根由后端自己构造**：`DslRoot(输入, 渲染器, 屏幕工厂, 根工具)` 是公开构造器，后端不需要实现
  `DslRootRenderer` 就能有根——根只要求一个渲染器**实例**（本仓是 `Recorder`）。`frame()` 里用
  `context(renderer, renderParam, input.mouse) { root.component.render() }` 把渲染器当 **context 实参**
  传进去；**不要 `by Renderer` 让别的角色冒充渲染器**——那会把两个角色的生命周期绑在一起。
- **`renderer == null` 不等于"不画"**：渲染器**同时是字体来源**（文字组件通过
  `context(renderer: DslRootRenderer<RP>) { renderer.getFont(...) }` 取字形）。把 `renderer` 设成
  `null` 会**连字体一起拿掉**。本仓渲染器恒非空；将来若做"无绘制订阅根"，不要用 `null` 表达它。
- **换核心之后要重建所有后端产物**：`run/mods` 里任何按旧核心编译的 jar 都会在启动时炸成
  `NoClassDefFoundError`（聚合 backend 已删）。这不是新代码坏了，是旧产物没重建——先重建再判断。
- **尺寸归驱动方**，不归根：根的职责是每帧**把 rect 写出去**，来源不归契约管。web 的尺寸来自客户端
  画布，所以记在记录器上、由驱动方在调 `WebBackend.frame()` 之前写入。
- **`DslRuntime.start` 返回 `false` 不是失败**：一个进程只认第一个发布者，所以第二个后端拿到 `false`
  是正常结果。它只表示"**本进程的工具不是我的**"，**不表示**"我不能工作"——根照样建、页面照样画，
  而且**页面的 store 用的是本端自己的 `WebUtils`**（翻译、世界状态仍归本端），只有 `dslUtils` 是
  别人的。本仓的发布会（`adoptRoot`）**不**在 `false` 上早退，只记一条 warn 说明工具归谁；这条由
  `ForeignPlatformTest` 钉住（先发布一个外来工具，再断言建根、渲染、以及 `store.utils` 仍是本端的）。

## 如何验证"两个后端同进程共存"

将来重验这件事，按下面这套走，不必重新发明：

1. **独立的测试类 + 独立 JVM**。`DslRuntime` 是进程单例：`install` 一次、`start` 只发布一次、
   **先发布者终身获胜** ⇒ 已经发布过本端工具的 JVM **赢不了**这场竞争，所以这一步必须发生在新进程里。
   本仓靠 `build.gradle.kts` 的 `forkEvery = 1` 提供"每个测试类一个新进程"，**不是可有可无的配置**。
   **若它失效，用例是红而不是绿**：第一句 `assertTrue(DslRuntime.start { ForeignUtils })` 就是
   **前提自检**（重复 `install` 会先抛）。代价不是静默通过，而是**报错指向"发布竞争"而不指向配置**
   —— 所以前提要写在用例上，而不是只写在构建里。
2. **不要走 `WebTestRuntime`**：它的职责就是发布本端工具。共存用例自建运行时。
3. **先发布一个外来工具**（自己实现一个 `DslPlatformUtils`，`translate` 返回可识别的字符串），
   断言它**赢了**。
4. **然后推本端**：`WebBackend.adoptRoot()` —— 它内部的 `DslRuntime.start { WebUtils }` 返回
   **`false`**，只记一条 warn，**根照样建起来**。直接调 `DslRuntime.start` 并断言返回 `false` 也可以。
5. **在本端建页、渲染**：`WebBackend.create(title) { … }.show()` → `WebBackend.frame(w, h)` ⇒
   断言 `Recorder.size > 0`。
6. **两条身份断言是这个场景的全部意义**：
   - `DslDataStore(WebUtils, WebBackend.root, …).utils === WebUtils`（页面问世界状态问的是
     **自己**的工具）；
   - `dslUtils === 外来工具`（进程级只认第一发布者；`dslUtils.translate(...)` 返回外来串）。
   ⇒ 合起来才是"**工具归进程、渲染归根**"。
7. **失败时最先看**：`DslRuntime.start` 是不是返回了 `true`（说明 JVM 被污染了，或用例跑在了别人
   之后）。这一条比断言消息更能定位问题。
